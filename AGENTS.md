# Stock Monitor 0.16 development performance contract

Work only in this dev tree; preserve Store 0.15 and user history.
New heavy operations (network, OHLCV/DQ/indicator calculations, large serialization, subprocess waits) must not run in the Tk main thread. Reuse Dispatcher and owned compute clients; do not add per-instrument threads or a parallel pipeline.
UI callbacks only capture bounded state and apply current results. Preserve identity/source/currency/DQ/input_revisions checks immediately before publication. Never cancel a writer mid-task for a UI selection change.
For dispatcher/cache changes use targeted tests including 53/200 synthetic jobs, relevant-input invalidation and stale-result rejection. Real Windows measurements must distinguish startup peaks, rendering callbacks and steady background load. Target250ms, document measured exceptions; do not claim PASS based solely on unit tests.
Do not modify trading rules or start the MCP13 metadata task while Performance Engine is active. Record stage status in MCP_016_CHECKPOINT_RU.md.

Owner standing rule (18Oct2026): carry an accepted scoped task through a verified working result; resolve ordinary technical dependencies with safe bounded alternatives. Stop only for a genuine access/resource blocker, required owner permission, unacceptable risk or exhausted limit. Preserve scope and evidence; never bypass stale/DQ safeguards.

Owner standing rule (10Nov2026): every completed Stock Monitor work stage must also have an evidence-based report in GitHub (normally Issue #5, plus the relevant PR/issue): changes, tests, outcomes, remaining limitations and rollback. A local/chat-only report is not sufficient. Keep private data and credentials out of these reports.

Owner reporting rule (22Nov2026): every report must state the initial number of errors in the explicitly defined scope/snapshot, the number personally corrected by Work, and the number still unresolved. Attribute autonomous CandlePilot repairs separately, never count them as Work's direct repairs or double-count overlapping parent/child scopes. Work's manual TV observation or code fix that enables a later CP repair must be described as such, not as a direct candle write. Keep resolved and outstanding dates/TF visible. If a comparable initial count was not captured, state that it is unknown instead of inventing a count.

Owner standing rule (11Nov2026): when Work fixes a candle/data-processing problem, implement the reusable remedy in the existing CandlePilot/runtime path where safe, record its cause, evidence, limits and targeted regression in the existing experience catalogue/checkpoint, and publish the stage to GitHub. Do not leave recurring problems dependent on manual per-stock intervention. Unknown evidence, new risk permissions and provider restrictions must remain explicit; the catalogue is not permission to fabricate data or execute arbitrary fixes.

For anticipated candle failures, add a reproducible negative/positive scenario and a bounded recovery rule to the existing CP mechanisms where evidence supports it. Keep historical fixes discoverable in the current experience catalogue. Do not promise universal self-repair or replace missing source evidence with assumptions.

Owner standing rule (14Nov2026): the owner pre-authorizes recurring same-listing candle timebase corrections matching the verified Meta/TradingView pattern for all current and future stocks; do not ask again for this same technical correction. Use complete independently confirmed GETTEX/EUR source data, keep original OHLCV and explicit correction provenance, revalidate identity/window/revisions immediately before writing and trigger normal DQ/CORE reassessment. An empty TV interval is not a fabricated candle or exchange NO_TRADES proof. Missing evidence, changed source facts, current quote freshness and risk remain blocking. This permission does not grant TradingView automation/data-use rights or unconditional trading readiness.
Owner standing rule (14Nov2026, full stock integration): a newly working stock is not finished at candle repair or CORE READY. Use the existing sequential admission and shared admitted universe to connect chart/indicator selection, Demo BUY/SELL selection, authorized ChatGPT PAPER orders, automatic V1 evaluation and execution, position valuation/protection, journal, and CP data priority. Verify the integration and persistence for each newly admitted stock; do not require a new owner request or hard-code another per-stock route. Keep existing DQ, identity, freshness, input revision, risk and execution gates; WAIT alone is not a technical defect. A closed market or stale quote must remain explicit, never become a forced admission/trade. Preserve account, strategy settings and current positions.

## История исследований V1–V5

- В начале каждого отчёта об исследованиях указывать явный итог «Положительные исследования — да» или «Положительные исследования — нет». При положительном результате перечислить точные названия исследований, период, чистый результат после издержек и статус проверки на новом периоде. Если данных недостаточно, прямо указать «Результат не определён» и причину. Правило действует для отчётов в чате, чекпоинте и GitHub.
- Перед поиском нового варианта или улучшением любой V1–V5 открыть [«История проверок V1–V5»](MCP_016_CHECKPOINT_RU.md#paper-strategy-research). Для выбранной стратегии прочитать применимые прогоны, базовую версию, причины WAIT/отказа/выхода, ограничения и ещё не проверенные гипотезы. Использовать уже сохранённые данные и результаты.
- Для исследования каждого торгового ТФ использовать последние 12 месяцев по тому же инструменту, площадке и валюте, где ряд позволяет. Дату начала и покрытие фиксировать для каждого ТФ. Если для части года имеются только аналитические свечи, отдельно оценивать сигнал, а итог исполнения проверять на доступных ценах заявки. Сравнивать отдельные правила для каждого торгового ТФ и проверять кандидатов на ранее не использовавшемся периоде.
- Повторять проверку только для конкретного вопроса: другой период, исправленные или расширенные данные, изменённое правило или исполнение, воспроизведение дефекта либо проверка перед внедрением. Записать отличие и ссылку на прежний результат.
- После каждого прогона добавить в тот же чекпоинт короткую запись и ссылку из указателя. Фиксировать дату, V1–V5 и версию/коммит, что именно менялось, инструменты/биржу/валюту, период и ТФ, источник и ограничения данных, базу сравнения, капитал, размер, издержки и способ исполнения. Сохранить число сигналов и отказов с причинами, сделки и выходы, плюсы/минусы, чистый P&L и просадку, а также вывод и оставшийся вопрос. Записывать нулевые, отрицательные, заблокированные и незавершённые проверки. Для заблокированной проверки указать причину и какие показатели невозможно оценить.
- Детальный журнал решений, сделок и примечаний, параметры и воспроизводимые файлы хранить в существующем СМ-Архив. В чекпоинте указать ссылки, статус («исторический тест», «теневой режим», «установлено в TEST», «активно») и отделять результаты исторического прогона от фактически исполненных PAPER-сделок в «Демо». При исправлении старого результата связать оба прогона и отметить, какой использовать.


## Язык внешней информации (правило владельца, 21.11.2026)

Показывать пользовательскую информацию на выбранном языке СМ (ru/de/en), включая заголовки и краткое содержание новостей. Сохранять оригинал отдельно, показывать отметку машинного перевода и доступ к оригиналу. Не переводить идентификаторы, фактические цены, источник и торговые данные; перевод не является новым рыночным доказательством. При недоступном или сомнительном переводе явно обозначать показ оригинала, не выдавать его за перевод и не придумывать содержание. Выполнять перевод вне Tk и переиспользовать только результат для того же исходного текста и языка.
